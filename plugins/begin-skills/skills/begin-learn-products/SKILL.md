# Learn products with Begin

Explain how a product helps its user complete a task, using evidence from its actual surfaces. Extract useful structure and interaction decisions; make the resulting design belong to the owner's product.

## Inspect a task, not a brand list

Start with the owner's audience, intended action, and the question the comparison should answer. Use the supplied products or find relevant examples when research is requested. Select by similar task, role, and business context, not just visual reputation. Keep the number and depth of references proportional to the decision.

Open the relevant pages or supplied artifacts with available browser, image, documentation, or file tools. Inspect the content before describing it. Follow the material navigation and core flow when access permits. A screenshot establishes a visible layout and state; it cannot establish a transition, submission result, private role, or backend behavior.

Record the product, exact URL or file, inspection date or supplied revision, observed page or state, and access limits. Public pages, official documentation, supplied screenshots, and authorized source code provide different kinds of evidence. Label behavior as **observed**, **documented**, **source-backed**, or **inferred** where that distinction matters. Do not use a search snippet or a generated style summary as evidence that a screen or interaction was inspected.

Read [mapping and transfer](references/mapping.md) for a concrete page/flow map or a comparison across products. Read [the worked comparison](references/worked-comparison.md) when evidence limits and transfer decisions need an example.

## Map the structure that matters

Capture the task's relevant roles and entrypoints, navigation groups, page purpose, core actions, important alternate paths, and visible states. Include loading, empty, invalid, denied, unavailable, or success states only when observed, documented, or required by the owner's proposed flow; mark their evidence accordingly.

Map the information each action reads or changes and the role allowed to use it. A form's fields suggest data needs for a proposed product; they do not reveal the reference product's database schema. Separate the website's direct user, their customer, and visitors where the workflow requires it. Name payer and payment receiver if a payment path is in scope.

When access is limited, continue with the available evidence and name the missing part. Do not infer that an unobserved page or state is absent. Avoid creating accounts, submitting messages or payments, or changing real records merely to complete a research map.

## Produce a useful structure brief

For a research request, return the observed structure, material comparison, sources, and limitations. For a proposed product, add the smallest page/flow map that serves its audience, with each page's job, key action, relevant states, and necessary data. Mark new decisions as proposals rather than discoveries about the references.

Explain what to reuse, why it fits, and where the pattern would fail. Borrow hierarchy, sequence, progressive disclosure, or a useful recovery behavior; create original brand, wording, visual composition, and assets. Do not copy private material, distinctive artwork, or entire screens.

Keep the deliverable proportional: an annotated list or table is often enough. A competitor's broad surface does not justify reproducing every feature. End with the most useful next design decision or the specific missing observation; do not automatically scaffold a project, generate a platform, or implement the comparison.
