# Keep the operation and its appearance together

Use this when a collection changes a preview, quantities change a result, or a person edits and keeps work. Keep the project's existing framework and state model.

## Identify the facts before drawing the transition

Name the selected record, current input, prepared result and kept version where those states exist. Give records stable identifiers. Render a selected item's name, facts, actions and selected styling from the same identity. A filter changes the visible collection; decide explicitly whether it also changes the selected item. Do not let a list position become a record identifier.

An editable note and its saved value are different states. Cancel restores the saved value. Saving confirms the actual write before showing success. When changing records with unsaved work, preserve it or make the discard choice clear. Choose the behavior that suits the task, then test it after switching to a second record and returning.

For quantities and money, preserve the source unit and use exact arithmetic suitable for the domain. Calculate money in minor units when prices use a fixed currency precision. Parse input with explicit bounds and allowed steps. Derive line totals, summary totals and exported values from the same prepared data. A decorative counter must end at the actual value and remain understandable during repeated changes.

## Add an effect to a usable base

Keep essential words and actions readable before enhancement. A hidden-on-mount wrapper can leave a whole offer or result unavailable when its script, font or observer fails. Provide a useful still state for optional art. Keep interaction targets stable while their surroundings move.

Use semantic links, buttons, inputs and disclosures where they fit. A draggable collection also needs an ordinary route to each item. A hover response needs useful focus and touch behavior. For a modal, test opening, initial focus, background interaction, keyboard containment, closing and focus return; a dialog role alone does not implement those behaviors.

If movement is useful, define what starts it, what interrupts it and what remains at rest. Honor a changed motion preference during the session. Stopping visible movement and stopping scheduled work are different checks. For continuous graphics, inspect offscreen and hidden-tab behavior, resource cleanup and a missing-graphics fallback. Use a simpler material when it communicates the same thing with less integration work.

## Treat local recovery as an optional operation

Browser storage can be unavailable, full, malformed or from an older version. Parse and validate recovered state before using it: object shape, known identifiers, supported status values, string/array limits and valid quantities. Reject unsupported shapes or deliberately normalize them; never trust unexpected fields. Render visitor text as text.

A failed save must leave current work usable and give an accurate recovery option. Automatic saving must not clear unrelated storage. A reset should affect only this example's own named state. Keep saved state versioned when its shape can change.

Follow an ordinary guide or detail link with changed work present, then return. An explicit Save button does not protect an unsaved working copy. If the task needs both automatic draft recovery and a deliberate checkpoint, store and name them separately. Verify each write before claiming protection. When recovery is unavailable, explain the consequence before navigation discards current work; a generic success message cannot replace that protection.

For an export, build the file from the current valid result. Include the names, units, conditions and relevant version that make it useful outside the page. Reject an empty or invalid result with an explanation. Report a created download separately from delivery to a service; a local collection list is not a submitted order.

## Check the complete change

Exercise one normal change, an interruption or cancellation, a different item and a return. Check the actual populated result at desktop and narrow widths, including long names and notes. Verify selection, counts, status text/color, arithmetic, focus and exported content. Then reload and inspect the kept version. Test invalid and denied storage when recovery is part of the example.

Source checks, browser observations and visual judgments establish different facts. Record the exact tested state and remaining limits. Keep a first complete source separate from later rendered repairs when comparing designs.

## Protect navigation when recovery fails

If current work cannot be saved locally, inspect every available route away from that work, including contextual help, footer links, home and notices. A protected header guide does not protect another link to the same destination. Keep the live work available through the chosen fallback, preserve the requested destination and fragment, and describe the limitation accurately. Apply this when work could otherwise be lost; do not force new tabs or departure warnings for ordinary saved navigation.
