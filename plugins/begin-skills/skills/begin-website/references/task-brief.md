# Define the current task

A useful working brief makes the next result and its completion clear. Reuse the person's request, accepted project records, and actual source. Ask only when a missing fact changes the work. Do not restart intake for an edit.

## Choose the necessary depth

For a small website, a short note can be enough: owner/visitor, purpose, content, main action, character, scope, and how the person will inspect the result. Keep it in the current project record when useful.

For a feature with roles, private records, payments, external effects, or work spanning sessions, also establish the important states, data/rule ownership, permissions, failure/recovery behavior, and observable checks. Reuse an existing spec. Add a separate behavior document only when it will materially help continuation or implementation.

A structure comparison is input, not automatically the agreed requirements. A visual direction describes presentation; the behavior contract should be able to accept more than one good presentation. Keep consequential engineering constraints visible before making incompatible interface promises.

## Two original examples

**Small service site:** An independent tutor wants families to understand lessons and contact them. Use their actual subjects, approach, availability explanation, and supplied email. With no photographs, recommend a strong typographic direction and an original lesson illustration. Initial scope is a service explanation and contact destination, not a booking system. Completion means a readable phone/desktop preview, accurate content, a meaningful requested edit, and the configured mailto destination opening. Email delivery remains outside that navigation check.

**Private enquiry:** A visitor submits name, reply address, and message to the intended website owner. Valid input is stored once; errors retain useful input. The recipient reads only their own records after verified sign-in; signed-out and other-owner reads are denied. A lost response allows inspection/retry without creating a second message. Completion includes real submission/read, denied paths, durable restart, and the owner's next requested edit. Notification delivery is a separate extension.

These are illustrative contracts. Do not copy their profession, field names, or states into an unrelated task.

## Record and use it

Distinguish accepted choices, a recommendation, and an unresolved fact. Link the relevant current files or provider configuration names without secrets. Keep `BEGIN.md` concise and point to a deeper artifact when needed.

Before implementation or an edit, locate the affected part of the contract. Afterward, check the agreed result and preserve unrelated behavior. For a request to define behavior only, deliver the brief and consequential questions without scaffolding a website. Do not create a spec file merely to complete a procedure.
