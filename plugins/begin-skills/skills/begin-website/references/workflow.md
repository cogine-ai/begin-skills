# Making and continuing a website

## Choose a useful starting point

Understand the website owner, visitors, and main visitor action. A service site usually helps a visitor understand an offer and make contact. A portfolio helps a visitor explore work. A product site explains a product and leads to a specific acquisition action. An editorial or documentation site helps readers find, understand, and use content. Treat these as starting structures; follow the person's actual purpose.

Inspect the working environment: project path, existing instructions, supported execution tools, Node availability for the supplied helpers, and the host's way of showing a preview. Use an available path rather than inventing a browser tool or installing a new framework by habit.

For a new site, first choose what the content needs: work that leads, a broad demonstration, a clear offer, an image scene, a useful collection, or an opening action. Select `service`, `portfolio`, `product`, or `editorial` for its useful source and behavior, create it in a new directory, and inspect its own guide before editing. State the destination. The helper must decline to overwrite an existing directory; choose another destination if it does. For an existing project, inspect its changes and use its own runner and dependencies.

## Shape the website

Use [a task-sized brief](task-brief.md) to establish purpose, agreed behavior, content, scope, and completion. For a small site, include visual character and a signature detail without adding a requirements ceremony. Give the person a proposal they can react to. Ask about a consequential uncertainty; avoid turning every typography or spacing decision into a question.

Replace sample identity and claims with supplied content. When material is missing, use clearly marked examples or write neutral descriptions. Decide where the main action goes. Keep unfinished destinations visibly recorded; never quietly substitute an unrelated booking or email address.

For a new substantial direction, compare two or three compact arrangements of the same headline, explanation, work and action before retaining the starter's layout. Change what leads, what shares a surface, and how the next section begins. Choose the arrangement that makes this visitor's decision clear, then build one coherent direction with useful interaction states and navigation on smaller screens. Keep accepted directions during routine edits.

Record a consequential font or layout choice and the next action in `BEGIN.md` before a long implementation step. Keep comparison files outside the served website. If the session stops, the next conversation should be able to continue the selected direction from the note and current files.

## Preview, edit, and check

Run the real project. For a supplied static site, use the owned background preview when the local host permits it, and retain its status and stop commands. A foreground process can end with its Agent tool session. Check reachability before handover, reuse the running process during later edits, and record how to restart it. Share the actual local URL or the host's supported preview surface. When browser tools are available, inspect the rendered pages at phone and desktop sizes and exercise the central action. When they are unavailable, say which observations remain open and give a workable preview path.

Read the whole page, including the opening's transition into evidence and the route to the action. Check the linked task or reading page with its real material. On phone, inspect where useful content begins, image crops, readable artifacts and the context before consequential controls. A strong opening needs a coherent continuation.

For an edit, locate the affected content and styles and preserve their current state before changing them. In Git, inspect the current changes and retain a scoped patch plus copies of affected untracked files when needed. Without a usable Git baseline, keep a copy of the affected files outside the served website directory. Do not use a whole-project reset to undo one edit. Apply the change and inspect the result; recheck nearby navigation and the central action. Avoid changing unrelated content to make a requested edit simpler.

## Continue or recover

Keep `BEGIN.md` concise: choices, resources, commands, stage, unresolved setup, and next action. Read it when resuming or changing hosts. Verify its commands against current files; a note is context, not proof.

If preview fails, read the actual process output, distinguish a stopped server from an inaccessible host preview, and restart only the relevant process. Port conflicts are solved by choosing an available port or stopping a process you started. Preserve the website files. If a dependency or credential is missing, continue useful local work and identify the specific setup needed.

Before publishing, inspect the exact directory, assets, configuration, and destination. Confirm existing authorization for that external action. A successful upload, an accessible public site, and a working visitor action are separate observations.
