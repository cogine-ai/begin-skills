Before you start

Work in your own copy of this website. Keep the original starter available as a reference. You need a text editor or an Agent that can edit files, and a browser. The pages use HTML, CSS, and JavaScript; there is no build step, account, or remote font to configure.

The result of this guide

You will have a publication homepage, one complete article, and one practical guide with working navigation. You will also have checked the source folder you plan to publish. This guide does not create a hosting account or deploy the website.

1Choose the writing

Decide who the publication is for and which question its first article should answer. Draft the whole article before adding more reading entries. A useful first edition can be small if every link has something complete behind it.

For a practical guide, name the outcome and the prerequisites. Put the actions in the order a reader must perform them. Explain how to tell whether a step worked, and what to do if it did not. Keep marketing promises separate from instructions a reader must follow.

The example article and guide are original sample material. Replace their author and publication details with accurate information. If any example remains, preserve its label so a reader can distinguish it from your own published work.

2Edit the three pages

Change the publication name in the header and footer of every page. Update each page title and description. Keep one main heading on each page, then use section headings to organize the text.

Where each part lives
FileWhat to edit
index.htmlThe introduction, featured article, supplementary reading entries, and footer.
article.htmlThe complete essay, author, headings, contents links, and related reading.
docs.htmlThe guide, prerequisites, ordered steps, checks, and troubleshooting.
common.cssShared colors, fonts, navigation, and footer.
index.cssThe homepage spread and supplementary reading entries.
reading.cssArticle and guide typography, reading width, contents, and responsive layouts.

When you change a heading's id, update any contents link that points to it. Keep file names and links aligned. A link to article.html#real-action opens a specific section; label it as a section rather than a separate article.

3Preview the reading experience

Ask your Agent to preview your working folder with its available local preview tool. Open the local address it returns. You can also open index.html directly in a browser; relative links lead to the other pages.

Read a few paragraphs on a phone-sized screen and a desktop. The text should fit comfortably, headings should remain understandable, and no horizontal scrolling should be needed to read the page. Check a middle width too: a layout can fail between its phone and desktop arrangements.

Use the keyboard to follow the main navigation, a reading entry, and a contents link. Focus should remain visible. Open and close the native contents disclosure. Turn off JavaScript and reload: the full article, guide, homepage entries, and contents links must still be available. JavaScript highlights the current section in the article and guide contents.

4Check every promised destination

From the homepage, open the complete essay and return. Follow the essay-section entry and confirm that it reaches the named section. Open the guide from both the header and the essay's related-reading link.

The homepage offers three reading destinations: the complete essay, this practical guide, and the essay's section on building a real action. Keep each label accurate when you replace the writing. The homepage footer's contact link uses a clearly labeled example address. Replace it with an intentional destination before publishing. An email link opens an email app and does not send a message on its own.

  • Every reading entry reaches a complete article, guide, or clearly labeled section.
  • Every contents link reaches the matching heading.
  • The publication and author details are accurate.
  • Remaining examples are labeled.
  • Any contact destination is intentional and clearly described.

5Prepare the publishing folder

Keep the three HTML files, common.css, index.css, reading.css, site.js, and the used art/ and fonts/ files together. Preserve their relative paths. Your host should serve the folder's index.html as its entry page.

Inspect what will be uploaded. Exclude private notes, credentials, local databases, and unused resources. Guidance files such as README.md and project records help you work, but are not needed by a visitor. Use your host's supported configuration to keep those files outside the published output.

After an authorized deployment, check the returned URL, intended audience, assets, and the same reading path you checked locally. A successful upload does not prove that a custom domain has finished connecting. Keep the previous useful version so you can recover from a failed update.

If something does not work

A link opens a missing page

Compare the link with the actual file name. Hosted file paths can be case-sensitive. If the file opens but a section link does not move, check that the destination's id exactly matches the link fragment.

The contents do not highlight a section

Confirm that site.js loads on the article and guide pages. Section highlighting also needs a browser that supports IntersectionObserver. The native disclosure, section links, and full text remain usable without highlighting.

The illustration is missing

Confirm that art/reading-path.svg is present at the expected relative path. The surrounding article stays readable without it. If you replace it, update its description and caption to describe the new image accurately.

An update changes the reading layout

Compare the changed selectors in reading.css and shared tokens in common.css. Repair the affected rule, then recheck narrow, middle, and desktop widths. Keep the content and working destinations intact while adjusting the layout.

This guide is original example content. It describes the supplied static files; no hosted deployment or visitor outcome is claimed.
